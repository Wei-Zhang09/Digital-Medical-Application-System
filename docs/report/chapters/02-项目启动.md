# 2. 项目启动

## 2.1 组织结构

本项目按「一人多角色」承担，覆盖软件企业里的完整岗位链。这样安排的原因是课程要求完整体验研发流程，而小组被压缩为个人完成，所以同一个人的不同阶段分别对应不同职位。

| 软件公司职位 | 角色职责 | 实训班级成员 | 本项目承担人 |
| --- | --- | --- | --- |
| 决策人员 | 立项决策、范围确认 | 机构领导 | 指导教师 |
| 项目管理者 | 计划、进度、风险管理 | 项目经理 | 张伟（兼） |
| 分析设计人员 | 需求分析、概要设计、详细设计、数据库设计 | 小组成员 | 张伟（兼） |
| 开发人员 | 后端编码、前端编码 | 小组成员 | 张伟（兼） |
| UI 设计人员 | 界面原型、交互与配色 | 小组成员 | 张伟（兼） |
| 测试人员 | 用例设计、执行、缺陷跟踪 | 小组成员 | 张伟（兼） |
| 客户及最终用户 | 需求确认与验收 | 指导教师 | 指导教师 |

## 2.2 进度计划与实际执行

任务书给定的节奏是 10 天 / 3 人组。本项目为个人完成，计划压缩到 7 个工作日；实际执行时因为开发资料（数据库脚本、素材、官方任务指导）齐备，并采用 AI 辅助编码，全部任务在 **1 个工作日内**完成。

| 阶段 | 计划 | 计划内容 | 实际 |
| --- | --- | --- | --- |
| D0 | 半天 | 环境修复、工程骨架、数据库导入 | 已完成 |
| D1 | 1 天 | 认证与权限闭环（JWT + 菜单树） | 已完成 |
| D2 | 1 天 | 8 类主数据后端 CRUD + 药品上传 | 已完成 |
| D3 | 1 天 | 前端请求层、登录、动态路由、药品页 | 已完成 |
| D4 | 1 天 | 其余 7 个前端页面 | 已完成 |
| D5 | 1 天 | 数据面板 + 销售地点地图 | 已完成 |
| D6 | 1 天 | 部署（jar + dist + Nginx）与测试 | 已完成 |
| D7 | 1 天 | 报告、答辩材料、打包 | 进行中 |

**进度偏差说明（如实记录）**：原计划 7 天，实际 12 个开发任务在 2026-11-05 当天 17:20 至 20:50 之间完成，约 3.5 小时。原因有三条：

1. 数据库脚本与素材由课程提供，省去了建库和造数时间；
2. 官方任务指导把每个模块的接口、字段、分层都写清楚了，减少设计返工；
3. 采用 AI 辅助生成模板化代码（8 个模块的 Controller/Service/Mapper 结构一致），人只做结构设计与验收。

这不是「计划失效」，而是估算基准不同：原估算按「从零摸索」的人力工期，实际执行是「有明确设计文档 + 工具辅助」。报告中保留计划表与实际表，便于对照。

## 2.4 配置管理

| 项 | 做法 |
| --- | --- |
| 版本库 | GitHub `Wei-Zhang09/Digital-Medical-Application-System`，主分支 `main` |
| 提交粒度 | 一个任务一次提交，提交信息带任务编号（如 `feat: 首页数据面板（T9）`） |
| 提交规模 | 21 次提交，264 个受管文件 |
| 代码规模 | Java 93 个文件约 3945 行；Vue 13 个文件约 2242 行；另有 26 个 JS、14 个 XML 配置与映射文件 |
| 分支策略 | 单人开发，采用主干开发 + 任务级提交；未启用特性分支（无并行开发需求） |
| 不纳入版本库 | `backend/target`、`frontend/node_modules`、`frontend/dist`、`.dev`（本地 Node/MySQL/Nginx）、`uploads` |

> 任务书原计划使用 CodeArts 做敏捷管理与代码托管。本项目未注册 CodeArts，改用 GitHub 完成同样的能力：提交历史即迭代记录，任务看板用本地 Hermes Kanban（14 张任务卡、依赖链、完成证据）。CodeArts 的思维导图、甘特图在本报告中以进度表替代。
