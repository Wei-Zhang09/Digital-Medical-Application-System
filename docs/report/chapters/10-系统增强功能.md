# 第 10 章 系统增强功能（第二轮迭代）

> 本章记录在官方任务清单全部完成之后，按《项目需求描述》与使用反馈补充的一轮增强。
> 官方 19 个后端任务、10 个前端任务与 2 项扩展功能均已在前述章节交付，

## 10.1 增强背景

首轮交付后对照《项目需求描述》与素材包做了两处核对，发现三类问题：

| 问题 | 依据 |
| --- | --- |
| 缺少注册页 | 前端素材包内存在 `Register.png`、`RegisterBackground.jpg`、`RegisterButton.png`，说明原系统有注册入口 |
| 缺少用户管理 | 需求 1.2 明确列出「用户管理模块」，但官方任务清单未给出对应任务 |
| 医师可见范围偏小 | 需求 1.3 写「医师可查看医药公司、城市信息、销售地点」，而官方 `bin_text.sql` 的 `role_permission` 只给 5 个菜单 |

此外还补齐了修改密码、操作日志、数据导出、排序与多条件查询、表单格式校验等
一个完整管理系统通常具备、但任务书未要求的能力。

## 10.3 关键设计说明

### 10.3.1 注册与账号体系

注册只创建 `account` 记录，角色固定 `ROLE_2`，**不写入 `doctor` 表**——
医师档案（职称、科室、所属医院）仍需管理员在「医生信息管理」中补全。
这样既满足自助注册，又不破坏 `doctor` 与 `account` 一对一的既有约束。

校验规则前后端一致：登录名 4–20 位（字母/数字/下划线/汉字）、密码 6–20 位、
手机号 11 位、两次密码必须一致、登录名唯一。

### 10.3.2 权限保护

账号管理模块设置了三条保护，避免管理员把自己锁死：

1. 不能删除当前登录的账号；
2. 不能删除最后一个管理员账号；
3. 不能把最后一个管理员降级为医师。

### 10.3.3 排序的注入防护

`ORDER BY` 无法用 `#{}` 占位，只能拼接。为此引入 `SortUtil` 白名单：
前端传入的字段名先查模块对应的映射表，命中才拼成 `列名 ASC/DESC`，
未命中直接忽略（不排序）。实测传入 `sort=drug_name;DROP TABLE drug` 时
接口正常返回且数据表完好。

### 10.3.4 导出的实现取舍

导出没有另写一套查询 SQL，而是**复用各模块的列表服务**（`pageSize` 取 10000 上限），
保证「导出内容 = 页面筛选结果」。医保政策与公司政策在导出时把 `city_id`/`company_id`
换成城市名与公司名，便于阅读。

前端未走 axios 实例：该实例会把响应当 JSON 解析并统一提示，二进制流走不通，
改用原生 `fetch` + `blob`，文件名从 `Content-Disposition` 解析。

### 10.3.5 操作日志的实现方式

采用 AOP 而非在每个接口加注解：切点为 `com.qst.medical.controller..*`，
拦截 POST/PUT/DELETE 且执行成功的方法，模块名按 URI 前缀推断、动作按 HTTP 方法推断。
新增接口只要路径符合约定，日志自动产生，不需要额外改代码。

写日志的异常只记 `warn`，绝不影响业务返回；登录与注册接口不记录。

## 10.4 与官方资料的差异说明

本轮有两处主动偏离官方素材，答辩时需要说明：

| 差异 | 官方原样 | 本项目 | 依据 |
| --- | --- | --- | --- |
| 医师角色菜单数 | `role_permission` 中 ROLE_2 仅 5 个菜单 | 8 个（补医药公司、销售地点、城市信息，只读） | 《项目需求描述》1.3 |
| 数据库名 | `bin_text` | `digital_medical_application_system` | 按用户要求统一改名，`sql/` 下脚本与配置同步更新 |

两处改动都通过 `sql/` 下的幂等增量脚本实施，不修改课程原始 `bin_text.sql` 的建表语句。

## 10.5 数据库变更

| 变更 | 说明 |
| --- | --- |
| 新增 `operation_log` 表 | 操作日志，8 个字段，`createtime` 与 `uname` 建索引 |
| 新增 `permission` 记录 | 「账号管理」「操作日志」两条菜单，均只授予 ROLE_1 |
| 新增 `role_permission` 记录 | ROLE_2 补 3 条只读菜单；ROLE_1 补 2 条 |

至此数据库共 **18 张表**。
