## 5.2 登录鉴权模块

**功能描述**：校验用户名口令，签发 JWT；后续每个请求由过滤器解析 token 并写入安全上下文。

**接口与属性**：

| 名称 | 说明 |
| --- | --- |
| `POST /api/login` | 表单登录，由 Spring Security 的 `formLogin` 处理 |
| `Msg` | 统一返回体，`code` 取值 20000/10000/10006 |
| `JwtUtil.getJwtToken(Long id, String uname, String role)` | 生成 HS256 token，载荷含 id/uname/role |
| `JwtUtil.getClaimsByToken(String token)` | 解析 token，异常统一返回 null |
| `JwtUtil.resolveToken(String header)` | 只接受 `Bearer ` 前缀，其它返回 null |
| `JwtFilter` | 位于 `UsernamePasswordAuthenticationFilter` 之前，解析 token 后把 `AccountDto` 放入 SecurityContext |
| `WebSecurityConfig` | 放行登录、Swagger、`/image/**`；其余需认证；STATELESS；开启 CORS；关闭 CSRF |

**处理流程**：

```
请求到达
  → JwtFilter 取 Authorization 头
      ├─ 无头/格式不对 → 不设置认证 → 继续过滤链 → 最终 10006
      └─ 有 Bearer token → 验签
            ├─ 失败（过期/篡改）→ 同上
            └─ 成功 → 构造 AccountDto 作为 principal + 角色 authority 写入上下文
  → Spring Security 判断路径与角色
      ├─ 未认证访问受保护路径 → AuthEntryPoint → 10006
      ├─ 已认证但角色不足 → AccessDeniedHandler → 10000 权限不足
      └─ 通过 → 进入 Controller
```

**关键设计取舍**：

1. 不用 Session，改 JWT 无状态认证——前后端分离部署时不需要共享会话。
2. 角色存在 `account.utype` 列（值为 `ROLE_1`/`ROLE_2`），登录查询时用 `utype AS role` 映射，上层只认 `role`。
3. 四类失败（未登录、认证失败、无权限、登录成功）分别由独立 Handler 处理，返回体结构与业务接口一致，前端只判断 `code`。

## 5.3 菜单权限模块

**功能描述**：按当前用户角色返回菜单树，前端据此动态挂载路由。

**数据结构**：`permission(id, pid, name, path, component, level, title)` + `role_permission(id, roleName, per_id)`。

**处理流程**：

```
GET /api/permissions
  → 从 SecurityContext 取 principal.role（不信任前端传参）
  → SELECT p.* FROM permission p JOIN role_permission rp ON rp.per_id=p.id WHERE rp.roleName=?
  → 把每行转成 PermissionModel（带 meta.title）
  → 取 pid=0 的行作为根（Layout、404）
  → 递归 selectChildren：找 pid == 当前节点 id 的行，挂到 children
  → 非 ROLE_1 时把标题里的「管理」替换为「查询」
  → 返回 {permissions: [树]}
```

**为什么菜单要在后端算**：菜单即权限的可视化结果。如果前端自己决定显示哪些菜单，用户改一下本地存储就能看到不该看的入口；虽然接口层还有 `@RolesAllowed` 兜底，但把菜单交给后端能让「看到的」和「能做的」始终一致。

## 5.4 药品模块

**功能描述**：药品的增删改查、图片上传、与销售地点的多对多关联。

**数据结构**：

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `drug` | drug_id、drug_name、drug_info、drug_effect、drug_img、publisher | 药品主表 |
| `drug_sale` | id、drug_id、sale_id | 药品与药店多对多关系 |
| `sale` | sale_id、sale_name、sale_phone、lng、lat、address | 销售地点 |

**接口**：

| 动作 | 方法与路径 | 角色 |
| --- | --- | --- |
| 分页查询 | `GET /api/drugs/{pn}/{size}?name=` | 已登录 |
| 详情（含 saleIds） | `GET /api/drugs/{drugId}` | 已登录 |
| 新增 | `POST /api/drugs` | 角色 1、2 |
| 修改 | `PUT /api/drugs/{drugId}` | 仅角色 1 |
| 删除 | `DELETE /api/drugs/{drugId}` | 仅角色 1 |
| 上传图片 | `POST /api/upload` | 角色 1、2 |

**处理流程（新增）**：

```
校验 saleIds 中每个药店是否存在（不存在 → 「销售地点不存在：xxx」）
  → 插入 drug，回填自增主键
  → 若 saleIds 非空：批量插入 drug_sale
  → 返回 20000
```

**处理流程（修改）**：先更新 drug 字段，再 **删除该药品全部 drug_sale 关系**，然后按新提交的 saleIds 重新插入。这种「整体替换」比逐条比对差异更简单，也不会留下脏关系。

**处理流程（删除）**：先删 `drug_sale` 中的关系，再删 `drug` 主表。`drug_sale` 没有外键约束，但顺序上先清子表更稳妥。

**列表查询**：用 `LEFT JOIN drug_sale + sale` 配合 `GROUP_CONCAT` 一次带出「销售药店」列，避免前端二次请求；分页由 PageHelper 拦截。

**图片处理**：上传接口把文件写入 jar 工作目录的 `uploads/`，文件名用 UUID 防重名，返回相对路径 `/image/xxx.png`；`ImageResourceConfig` 把 `/image/**` 映射到该目录。库里只存相对路径，开发态由前端拼 `http://localhost:8080`，生产态由 Nginx 反代，换机器不会裂图。

## 5.5 其他模块设计要点

| 模块 | 设计要点 |
| --- | --- |
| 医生信息 | 新增医师时**同步创建账号**：登录名按「姓名 + 手机号后 4 位」生成（如 `王小明4125`），初始口令 123456 的 BCrypt 密文，`utype=ROLE_2`；删除医师时连带删除账号；修改时同步账号的姓名与手机号；重置口令只改 `account.pwd` |
| 医药公司政策 | 新增/修改前校验 `companyId` 存在，不存在抛业务异常；列表不返回公司名，前端用 `/api/companies/all` 的字典把 id 映射成名称 |
| 医保政策 | 同理校验 `cityId`；该表 `create_time/update_time` 是 varchar，实体用 String 承接，写入时格式化为 `yyyy-MM-dd HH:mm:ss` |
| 城市信息 | 官方需求只有增、查、删，不提供修改接口；前端页面也不放「编辑」按钮 |
| 销售地点 | 基础字段 + 扩展的经纬度与地址；地图页用全量 `/api/sales/all` 渲染标记，列表页用分页接口 |
| 必备材料 | 最简单的模块，作为「新模块怎么加」的模板：各层各一个类 + 前端一个页面 + 一条 permission 记录 |
| 数据面板 | 计数用 4 条 `COUNT(*)`；职称与科室用 `doctor` 左连 `doctor_level`/`treat_type` 分组；资讯用三张内容表 `UNION ALL` 后按时间倒序取 5 条 |
